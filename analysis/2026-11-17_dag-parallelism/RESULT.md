# タイル QR の初めと終わりの並列度の不足を DAG から見積もり、τ と分ける（2026-11-17）

計測はしていない。PLASMA のコードから DAG を作り、p = 192 のリストスケジューリングで模擬した。実測は 3agg（`analysis/2026-11-17_flow2-perf-ratio-3agg/data/a_curves.csv`）の集計済みの曲線をそのまま使った。

## 1. 結論

1. **並列度の不足（初めと終わりにワーカーが空く時間）は、モデルの D の項にすでに入っていて、それを超えない。** PLASMA の DAG のクリティカルパスはちょうど D = 30N − 28 で（`data/a_dag_shape.csv`）、当てはめなしのモデルの時間は W/p + D そのもの（c = √7.5、k = 2 のとき η の項 ＝ D の時間）。空いたワーカーがすぐ次のタスクを取るなら、Brent の定理から模擬の時間は W/p + D を超えない。実際、模擬の時間はモデルの 0.61〜0.84 倍だった。**したがって並列度の不足では、実測がモデルより遅いことを説明できない。**
2. **予測 nb（32〜128）では、並列度の不足は余分な時間の 0.3% 以下。** 予測 nb では 192 本が埋まり、空きは初めより終わりのほうが大きい。それでも 0.2〜4.5 ms しかない。実測の余分な時間は 0.6〜3.4 s。
3. **実測の最適 nb（176〜408）では 192 本が一度も埋まらない**（同時に動くタスクは最大 10〜147 個）。時間はクリティカルパスで決まり、並列度の不足は余分な時間の **18〜38%**（MaxIB の A・β では 16〜36%）。残りは 13〜202 ms。
4. **残り（τ の候補）は「size で決まる一定の時間 c0 ＋ タスク数 × τ」の形でよく合う**（速い水準、size ごとの相対誤差 RMS 3〜6%）。τ = 8〜19 µs、c0 = 13 / 19 / 48 / 169 ms（size 1024 / 2048 / 4096 / 8192）。c0 は行列の大きさにほぼ比例する（約 9 ms ＋ 0.31 ms/MB）。

## 2. データの確認

- **DAG（PLASMA 548e0bd、`~/Download/build_plasma/plasma`）**
  - `compute/pdgeqrf.c:39-76`：平らな木（flat tree）。列 k ごとに DGEQRT(k,k)、DORMQR(k,n)（n > k）、DTSQRT(k,m)（m > k）、DTSMQR(k,m,n)。この順に主スレッドがタスクを作る（`compute/dgeqrf.c:146-157`、`#pragma omp parallel` + `master`）
  - depend 句：DGEQRT は A(k,k) inout・T(k,k) out（`core_blas/core_dgeqrt.c:178`）。DORMQR は A(k,k)・T(k,k) in、A(k,n) inout（`core_dormqr.c:244`）。DTSQRT は A(k,k)・A(m,k) inout、T(m,k) out（`core_dtsqrt.c:220`）。DTSMQR は A(k,n)・A(m,n) inout、A(m,k)・T(m,k) in（`core_dtsmqr.c:260`）
  - その結果、DTSQRT(k,m) は m の順に1本の鎖になる（すべて A(k,k) を inout）。DTSMQR(k,m,n) も列 n ごとに m の順の鎖になる（A(k,n) を inout）
  - **余分な依存（WAR）**：DORMQR は A(k,k) を in で読むので、DTSQRT(k,k+1)（A(k,k) を inout）は列 k の DORMQR がすべて終わるまで始まらない。クリティカルパスへの影響は定数 6（単位 nb³/3 flop）だけ（WAR あり 30N − 28、なし 30N − 34。`data/a_dag_shape.csv`）。スライドにあった 30N − 34 は WAR を除いた値と一致する
  - タイル形式への写し・戻し（`compute/pdge2desc.c:38-56` の dlacpy タスク）も同じ並列領域のタスクで計時区間に入るが、模擬には入れていない（重みが決められないため。「気になる点」）
- **重み**：flop 数（DGEQRT 4/3·d³、DORMQR 2·d_k²·d_n、DTSQRT 2·d_m·d_k²、DTSMQR 4·d_m·d_n·d_k。最後のタイルは端数の大きさ）÷ (A·E(nb))。総仕事量は 4N³（単位 nb³/3）で STATUS の W と一致した。端数のタイルがあると、flop の合計は flops_dgeqrf より 0.02〜0.15% 小さい
- **模擬の仮定**：ワーカーは p = 192 本。タスクは時刻 0 にすべて作られている。空いたワーカーが、準備のできたタスクを「準備ができた時刻の早い順（同時ならタスクを作った順）」に取る（fifo）。感度として「クリティカルパスの残りが長い順」（cp）も模擬した。予測 nb では空きが 18〜23% 減るだけで、最適 nb では同じになった（ワーカーが余っていれば、どのタスクもすぐ始まり、時間はクリティカルパスそのものになる）。タスクを取る時間、カーネルが全コアで動くときの遅れ、スレッドの起動は入れていない
- **実測**：3agg の a_curves.csv の fast・slow・mean（GFlops、ib について最大）を、flops_dgeqrf(size)/G で時間に直した。3agg のとおり、予測 nb では「遅い水準だけ」が「5回の平均」とほぼ同じ（size 1024〜4096 の予測 nb では同じ値）
- 模擬した nb：size 1024〜4096 は nb 32〜512 の 4 刻み（全格子）、8192 は nb 64〜512 の 8 刻み（nb < 64 はタスクが 100 万個を超えるので外した。予測 nb 104・128 は入っている）

## 4. 言い方の注意

言ってよい
- 「PLASMA の DAG のクリティカルパスはちょうど 30N − 28 で、モデルの並列効率の項（E_並列）は、この D を使った Brent の上限 W/p + D と同じ時間になる。だから、初めと終わりにタスクが足りない時間は、モデルにすでに上限として入っている」
- 「p = 192 で DAG を模擬すると、予測 nb では 192 本が埋まり、空きは余分な時間の 0.3% 以下。最適 nb の付近では一度も埋まらず、並列度の不足は余分な時間の 2〜4 割」
- 「残りの 6〜8 割（予測 nb ではほぼすべて）は、DAG の形では説明できない。size ごとの一定の時間と、タスク1個あたり約 10〜20 µs の時間でよく合う」

まだ言えないこと
- 「τ は 10〜20 µs と決まった」「τ はタスクの生成の時間」（size ごとの当てはめで、4 size 共通では合わない。中身は確かめていない）
- 「c0 はタイル形式への写しやページフォルトの時間」（行列の大きさに比例することまでしか分かっていない）
- 「並列度の不足が外れの原因ではないと証明した」（模擬は、タスクを取る時間、全コアで動くときのカーネルの遅れ、スレッドの起動を入れていない。言えるのは「カーネルの時間が1コアのままなら、DAG の待ちはモデルの D を超えない」まで）
- スライド・図では η と書かず、E_並列 と書く

## 気になる点・判断を保留したこと

- **予測 nb での余分な時間（0.6〜3.4 s）は残りとして扱ったが、τ の当てはめ（表C）には入れていない。** 速い水準が当てにならない nb の範囲（11-10 report.md C 節）だから。予測 nb での残り ÷ タスク数は 15〜73 µs で、表C の τ（8〜19 µs）より大きい。小さい nb では1個あたりの時間が大きくなるのか、集計が当てにならないだけなのかは決めていない
- **c0 が行列の大きさに比例するのは推測の手がかりにとどまる。** タイル形式への写し・戻し（dlacpy タスク）、タイル形式の A・T の最初のページフォルト（plasmatest-threads の RESULT 1.1 の 8）、free（munmap）はどれも計時区間に入っていて、行列の大きさに比例する。どれかは確かめていない。dlacpy タスクを模擬に入れなかったのは、1コアのコピーの速さが分からないため
- 式2の r0 は size 8192 で 1.86 になり、意味が通らない。残りに「計算の時間に比例する部分」があるかは、このデータでは決められない
- 4 size 共通の τ では合わない（RMS 14〜16%）。STATUS 問題5の「τ = a·p で全機種共通」の形を不老・弐にそのまま当てるのは難しそう。司令塔で STATUS を直すかの判断が要る
- 3agg と同じく、予測 nb の「遅い水準だけ」は、遅い水準を正しく選んだ値ではない
