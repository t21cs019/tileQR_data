## 0. 要点（スライド用）

- **D = 30N − 34、W = 4N³ は、Bouwmeester 型の依存（RAW のみ）なら N = 2〜64 のすべてで厳密に一致する。** ただし PLASMA 25.5.27 の実装は OpenMP の `depend` をタイル単位で付けるため、論文にない WAR 依存が1本増える。そのため実際の DAG では **D = 30N − 28**（+6 = UNMQR 1個分）になる。
- **モデルが崩れる条件は2種類あり、ずれの向きが逆。**
  1. **多コア・小行列（W/(pD) ≲ 1.4）：予測 nb が小さすぎる。** W/(pD) < 1.5 の11条件のうち10条件が性能比 95% 未満。実測は、コアを遊ばせてでも大きいタイルを選んでいる。
  2. **HT 有効構成と大行列：予測 nb が大きすぎる。** 予測が上限 512 に張り付く。HT 有効21条件のうち11条件が 95% 未満。W/(pD) は十分大きいので、並列度不足では説明できない。
- **「並列度不足で崩れる」という仮説は、条件の切り分けとしては当たっている。ただし向きはモデルの想定と逆。** DAG を厳密にスケジューリングした η を使っても、多コア側の予測はむしろ悪化する。崩れの原因は η（並列効率）の不足ではなく、多コア時に小さい nb で実効性能が E(nb) より大きく落ちることだと読める（観察。原因は未検証）。
- **c は理論値 √7.5 に固定してよい。k だけフィットすれば、性能は現行と同等（LOAO で 96.3% 対 96.2%）。** 一方、k = 2 や DAG シミュレーションを含む完全に計測なしの定式は、どれも現行より悪い。

### Q5. PLASMA のバージョンと dgeqrf の分解方式

- **バージョン**：PLASMA **25.5.27**（`~/Library/plasma/include/plasma_types.h` の `PLASMA_VERSION_*`）。ソースは `~/Download/build_plasma/plasma`、git **548e0bd**。
- **分解方式：TS カーネルのフラットツリー。** 根拠は3つ。
  - `compute/zgeqrf.c:262-266`：`householder_mode == PlasmaTreeHouseholder` のときだけ `plasma_pzgeqrf_tree`（TT カーネル）に入り、それ以外は `plasma_pzgeqrf` を呼ぶ。
  - `control/context.c:177`：既定値は `PlasmaFlatHouseholder`。`test/test.c:420` の `--hmode` も既定は `f`。
  - `tileQR_bench/src/run_time_dgeqrf.py`：`plasmatest dgeqrf --dim --nb --ib` だけを渡していて `--hmode` を指定していないので、**全計測はフラット（TS）**。
- `compute/pzgeqrf.c` のループは GEQRT(k) → UNMQR(k,n) → [TSQRT(m,k) → TSMQR(m,n,k)]（m = k+1..）。Bouwmeester の FlatTree(TS) と同じ形。
- **論文の DAG との違い**：`core_zunmqr.c:244` は `depend(in: A(k,k))`、`core_ztsqrt.c:220` は `depend(inout: A(k,k))`。このため OpenMP は TSQRT(k+1,k) を全 UNMQR(k,n) の後に回す（WAR）。実際に UNMQR が読むのは A(k,k) の下三角（V）、TSQRT が書くのは上三角（R）なので、数値的には不要な依存。§3 で影響を評価した。

### 2.4 言語化（A-5、データからの観察として）

1. モデルが崩れるのは、主に **W/(pD) が 1 前後より小さい条件**（p ≥ 24 の多コアで size ≤ 8192）。つまり実測最適 nb でも、コアあたり1本分の仕事しか DAG に無い領域。
2. ただしこの領域では、モデルは**並列度を確保するために nb を小さくしすぎる**。実測は、コアが遊んでも大きいタイルを選んだほうが速い。モデルの前提「小さい nb のコストは単体 DTSMQR の E(nb) で表せる」が、多コア・少タスクの条件で成り立っていない可能性が高い（タスク管理のオーバーヘッドや、多数のコアが小タイルを同時に回すときのメモリ帯域が候補。未検証）。
3. もう一つの崩れ方は **HT 有効（と一部の大行列）**。並列度は十分なのに、実測最適 nb が size とともに伸びない。前提「E(nb) は nb とともに単調増加し、上側を抑えるのは η だけ」が、キャッシュを共有する条件（HT は同一コアの L1/L2 を2スレッドで共有）で崩れている。`studies/ssrfb_parallel_contention`（共有 L3 で大 nb ほど性能が落ちる）と同じ向きの現象。
4. 現行の k = 1.35（理論値の 2 より緩い）は、この2種類のずれを1本の曲線で折衷した結果と読める（§4 の図）。

### 3.2 クリティカルパスの中身（B-3）

N = 3（D = 56）：
GEQRT(0,0)[4] → TSQRT(1,0)[6] → TSMQR(1,1)[12] → TSMQR(2,1)[12] → TSQRT(2,1;k=1)[6] → TSMQR(2,2;k=1)[12] → GEQRT(2,2)[4]

N = 4（D = 86）：
GEQRT(0,0)[4] → TSQRT(1,0)[6] → TSMQR(1,1)[12] → TSMQR(2,1)[12] → TSMQR(3,1)[12] → TSQRT(3,1;k=1)[6] → TSMQR(3,2;k=1)[12] → TSQRT(3,2;k=2)[6] → TSMQR(3,3;k=2)[12] → GEQRT(3,3)[4]

（PLASMA 版は GEQRT(0,0) と TSQRT(1,0) の間に UNMQR(0,1)[6] が入る。）

**30N − 34 になる理由**：経路は「最初のステップで列1を縦に下り、そのあと最下行を横に進む」L 字形をしている。

- 最初と最後の GEQRT：4 + 4 = 8
- ステップ 0 の TSQRT(1,0)：6
- ステップ 0 で列1のタイルを TS の連鎖で上から下まで更新する TSMQR(1..N−1, 1, 0)：12(N−1)。フラットツリーでは A(0,1) を全行が順番に書き換えるので、この連鎖は逐次になる
- ステップ k = 1..N−2 ごとに、最下行で TSQRT(N−1,k) → TSMQR(N−1,k+1,k)：18(N−2)

合計 8 + 6 + 12(N−1) + 18(N−2) = **30N − 34**。N が1増えると、縦の連鎖に TSMQR が1個（+12）、横の進行に1ステップ（+18）加わって +30 になる。

**指示書の導出との関係**：W/D ≈ 4N³/(30N) から pD/W ≈ 7.5p·nb²/size² となり、c = √7.5 ≈ 2.74, k = 2 という理論値の導出は DAG と整合する。PLASMA の実装依存（+6）を入れても、D の主要項 30N は変わらない。

**有望なのは (ii)：c = √7.5 を DAG から決め、k だけをフィットする方針。**

- **性能は現行と同等。** LOAO で平均 96.3% 対 96.2%、追加45条件で 94.0% 対 94.1%。自由パラメータは2個から1個に減る。
- **c は §3 で検証した W = 4N³, D ≈ 30N から導け、フィットした値とも近い。** 現行 c = 2.564 対 √7.5 = 2.739、差は 7%。PLASMA の実装依存（30N − 28）を入れても主要項は変わらない。
- **k はフォールドの間で安定。** 1.27〜1.40。

一方、**計測なしで k まで決める方法（(i), (iii), (iv), (v)）は、どれも現行より悪い。** DAG シミュレーションのような厳密な η ほど悪くなる。§4.1 のとおり、k は並列性以外の効果（多コア時の小 nb の損失、キャッシュ共有による大 nb の損失）も吸収している。したがって「c, k を両方とも測らずに決める」ことは、現在の E·η の積の形のままでは見込みが薄い。理論で決められるのは c までで、k を理論で決めるには、E(nb) 側に多コア時の補正を入れる必要がある（今後の課題の候補）。

## 5. 確認事項

**ノートと指示書の食い違い**

1. **現行モデルの定義**：vault（`notes/performance_model.md`、`STATUS.md`）の「現行モデル」は第4世代（改善C、c2=3.40, m=0.240, δ=0.715, k0=2.41）。指示書の第3世代 c = 2.564, k = 1.352 は vault には無く、`tileQR_data/derived/fold_constants.csv`（`scripts/fold_constants.py`）にだけある。さらに `tileQR_bench/tuning/model_predict.py`（Optuna 用の正典実装）は別の第4世代定数（C2=3.43, M=0.19, δ=0.836, K0=2.3、「55条件 LOMO 検証済み」）を使っている。**どれをゼミの「現行」とするか**の確認が必要。
2. **vault の第3世代の c**：vault では「c ≈ 2.1 が3機種で一致」。指示書 2026-09-06 では c = 2.919, k = 1.207（56群・β固定）。今回は c = 2.564, k = 1.352。3つとも条件（対象群・β）が違う。
3. **導出（W = 4N³, D = 30N − 34, Brent）は vault に記述が無い。** `notes/tileqr_algorithm.md` は「総タスク数÷クリティカルパス長から √p」と書くだけで、「総タスク数」と書いている（重み付き仕事量 W ではない）。Bouwmeester と Brent の PDF は vault の `refs/pdf/` に git 未追跡で置かれているだけ。
4. **D の式**：論文の依存なら 30N − 34 で正しい。PLASMA 25.5.27 の実装（タイル単位の OpenMP depend）では WAR 依存のため 30N − 28。発表で「PLASMA の DAG」と言う場合は注記が必要。また N ≥ 3 の条件は不要で、N ≥ 2 で成り立つ。
5. **カーネル名**：`notes/tileqr_algorithm.md` は DTPQRT/DTPMQRT と書いているが、PLASMA 25.5.27 の `pdgeqrf.c` が呼ぶのは `core_omp_dtsqrt` / `core_omp_dtsmqr`。
6. **「HT 有効4機種」**：データ上の SMT-on 構成は5つ（i7-7700, i3-7100, i3-10100, R5-7400F, R7-5800X）。R7-5800X HT は以前からあったものかもしれないが、区別できなかったので全部を追加側に入れた。
7. **「2ソケット EPYC 7702」が先週の追加か**：aoba-b_s2 の計測日は 2026-06〜09。calc_s2（2ソケット Xeon, 24コア）も40条件の外にあり、追加側に含めた。
8. **「p は物理コア数」と HT の結果**：HT 構成で p をスレッド数にすると性能比が上がる（HT 平均 94.5% → 96.2%）。vault の確定知見（Ryzen 5 7400F の外れ値が物理コア数で消えた）と矛盾する可能性がある。Intel の HT 構成だけで起きていて、R5-7400F HT では物理コア数のほうが良い。

**データの欠け・品質**

9. 全探索の欠け：calc_s2 8192、R7-5800X HT 8192（計測中）、i3-8100 16384（quarantine）。i7-7700 HT 16384 は2 trial・1ノードで計画外。
10. β の品質：Xeon E3-1220v3 は SSRFB 4本中2本が MRE 基準で落ち、2本平均。epyc-7543 は3本、R7-5800X は2本。HT 構成の β は SMT-off 用（threads=1）の流用。
11. **崩れた条件の多くで、COVERAGE の95%帯が退化**している（aoba-b s1 1024、s2 1024/2048/4096、calc_s2 1024、R7-5800X HT 1024/2048）。i3-7100 HT はサーマルドリフトが未除外（TODO_REMEASURE）。崩れの一部は計測ノイズの可能性がある。
12. `kurzak.py` の除外リスト（i3-7100 全体、epyc 1024/2048、i5-8500 8192）と vault の「データ品質の注意」に対し、`fold_constants.py`（96.2% の出典）は**除外せずに全40条件を使っている**。今回もそれに合わせて除外していない。

**判断に迷った点（こう決めた）**

13. β：中間40条件は `fold_constants.py` にハードコードされた値（例：aoba-b 186.3、i5-8500 170.0、i7-7700 169.5）。SSRFB から再計算した値（186.6 / 166.5 / 174.5 など、指示書 2026-09-06 の表と一致）とは少しずれる。96.2% を再現するために前者を使った。ハードコード値の出典（「指示書 2節の表」）は確認できなかった。
14. 予測は実測格子 [32, 512] 上の argmax。aoba-b_s2 / calc_s2 の 4096 は nb = 20 から測っているが、32 未満は捨てた。
15. 「性能比」の主列は、中間40は LOAO、追加は全点fit（どちらもゼロショット）にした。全点fit の値も表に並べてある。
16. vault は `~/tmp/tileQR_research`（git, 2026-10-21 時点）を正とした。`~/work/tileQR_research` は 2026-08-29 時点の古いコピーで、notes が1本しか無い。
17. 出力は tileQR_data の中の `analysis/2026-10-21/` に置いた（未追跡ファイル。コミットはしていない）。

## 6. 使ったスクリプト

すべて `~/src/tileQR_data/analysis/2026-10-21/scripts/` にある。実行は `~/src/tileQR_data/.venv/bin/python`。

| パス | 内容 |
|---|---|
| `scripts/common.py` | 共通層。データ読み込み（`kurzak.load_qr_curves`）、β の算出（SSRFB → MRE 5% 除外 → arch 平均）、η の各定式 |
