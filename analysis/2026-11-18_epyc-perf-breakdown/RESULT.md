# EPYC 7543 で QR の時間の内訳を測る：c0 と τ の切り分け（2026-11-18）

指示書：`~/Documents/tileQR_research/chats/2026-11-18_epyc-perf-breakdown_brief.md`。手順と条件：`INSTRUCTIONS.md`。

**この結果は EPYC 7543（p = 32 と p = 8、libiomp5、OpenBLAS）のものである。不老・弐（p = 192、libgomp）の c0・τ にそのまま当てはめない。** 不老・弐の c0（13〜189 ms）と、ここで出す値を直接比べない。

データ：`data/epyc_s1_smt-off_perf-breakdown_20261118_095221/`（plain・ref・perf、5 round）、`..._102530/`（strace、3 round）、`preflight_20261118_094626.txt`。計測は EPYC 7543（`kubota`）、カーネル 5.15、`perf_event_paranoid=0`・`kptr_restrict=1`（カーネルの symbol は解決できない）、THP は madvise。plasmatest は `/usr/local/lib` の libplasma と libopenblas（`libopenblas_zenp-r0.3.30.dev`）と libiomp5。

## 1. 結論

1. **nb 32（タスクが多い）・p = 32 では、計時区間のオンCPU の約 65% が OpenBLAS の `blas_memory_alloc`／`blas_memory_free` の中だった。** p = 8 では約 20%。nb 192 では 1% 以下。libiomp5（タスクの取り合い・待ち）は nb 32・p = 32 で約 10%、カーネルは約 1%。
2. **τ（タスク1個あたりの余分な時間）の大部分は、この OpenBLAS の割り当ての中にある**（p = 32：τ 3.5〜3.6 µs のうち 2.5 µs。libiomp5 は 0.3〜0.4 µs、カーネルは 0.03 µs）。ただし割り当ての中で何が時間を使っているか（ロック、探索、`mmap`）は分かっていない。
3. **c0 側（nb 192 でも残る、計算以外の時間）の中身は、起動（スレッドの生成）、QR の終わりの並列度の不足、最初のページフォルトの3つが混ざっている。** スレッドの生成は 31 本が **p = 32 で約 6.6 ms、p = 8 で約 1.4 ms** にわたって逐次に作られ（1本 約 0.2 ms）、11-10 の「1回目は約 6 ms 長い」と合う。カーネル時間は QR の初めに集中し、size 4096→8192 で 3.3〜3.9 倍（行列の大きさ ×4 に近い）。
4. `perf`・ref による時間の変化はない（perf／plain 0.98〜1.01、ref／plain 0.985〜1.012。size 512 を除く）。他のユーザーの CPU 使用率は全実行で 1%。

## 4. c0 と τ·タスク数への分け（完了条件②の後半）

各区分のコア秒 C を「c0 ＋ τ·タスク数」とみなし、同じ size・p の nb 32 と 192 の2点から解いた（`scripts/d_c0_tau.py`、`data/d_c0_tau.csv`）。**2点を通る直線であって、当てはまりの確認ではない。** 壁の時間の相当 ＝ コア秒 / p。τ は (T32 − T192)/(N32 − N192)。

**τ（µs / タスク）**

| p | size | τ 全体 | BLAS alloc/free | libiomp5 タスク＋その他 | カーネル等 | 計算（OpenBLAS＋core_blas） |
|---|---|---|---|---|---|---|
| 32 | 4096 | 3.62 | **2.51** | 0.39 | 0.03 | 0.65 |
| 32 | 8192 | 3.54 | **2.48** | 0.36 | 0.03 | 0.65 |
| 8 | 4096 | 3.49 | 0.83 | 0.72 | 0.13 | 1.77 |
| 8 | 8192 | 3.51 | 0.82 | 0.73 | 0.12 | 1.81 |

- 区分の合計は τ 全体に合う（p = 32、4096：2.97 ＋ 0.65 ＝ 3.62）。p = 32 では τ の約 7 割が BLAS の割り当て、約 1 割が libiomp5、約 2 割が計算（E_カーネル。nb が小さいとカーネルが遅い分）
- BLAS alloc/free の τ は p = 8 → 32 で 0.82 → 2.5 µs（壁の相当で 3.0 倍、コア時間では 1 タスクあたり約 6.6 → 80 µs）。libiomp5 とカーネルは p が増えても増えない
- **BLAS alloc/free は2点の直線に乗らない。** c0 側が負になる（p = 32：−8 ms、−59 ms）。nb 192 では1タスクあたりの alloc が 0.4 µs と、nb 32 の 2.5 µs より小さい。呼び出しの頻度で増える（競合する）形で、「タスク数に比例する定数 τ」ではない
- 11-10・11-11 の τ（2.0〜3.4 µs、p = 4〜32、nb 32）は p = 1 や p = 4 を基準にした値で、ここの τ 全体（p = 32 で 3.5〜3.6 µs）は nb 192 を基準にしている（計算の効率の差を含む）。定義が違うので、同じ量とは言わない

**c0 側：nb 192 の計算以外の時間**（壁の相当 [ms]。`data/d_c0_tau.csv` の `_at192_ms`）

| p | size | Time | 計算以外 合計 | カーネル等 | libiomp5（タスク＋その他＋待ち） | CPU 外 | BLAS alloc | libc |
|---|---|---|---|---|---|---|---|---|
| 32 | 4096 | 166 | 49（29%） | 7.2 | 35.6 | 3.1 | 1.5 | 1.2 |
| 32 | 8192 | 1014 | 106（10%） | 23.7 | 31.0 | 37.7 | 8.7 | 4.9 |
| 8 | 4096 | 398 | 37（9%） | 11.6 | 9.7 | 9.1 | 2.4 | 4.4 |
| 8 | 8192 | 2957 | 124（4%） | 45.3 | 24.6 | 28.6 | 11.2 | 14.4 |

- **起動（スレッドの生成）**：31 本の FORK が p = 32 で 6.6 ms（size 512）・5.0 ms（8192、nb 192）、p = 8 で 1.4 ms にわたる（`perf script` の FORK の時刻。perf による遅れを含む）。この間、CPU の使用率は p = 32 で 6% から 98% まで約 6.4 ms かけて上がる（`data/b_r1_fixed/*_catbin.csv`）。size によらない固定の時間
- **QR の終わり（並列度の不足）**：libiomp5 の待ち・タスクの試料の 46〜75% が区間の最後の 10% に入り、CPU の使用率は最後のビンで 38〜100%（p = 32・8192・nb 192 は 38%）（`data/e_start_end.csv`）。「CPU 外」もここに入る。11-17 の DAG の見積もりが対象にした並列度の不足と同じ側
- **カーネルの時間（ページフォルトを含む）**：nb 192 ではその 76〜85% が最初の 10% に入る（QR の初めのタイル形式への最初の書き込み）。size 4096→8192 で p = 32 は 3.3 倍、p = 8 は 3.9 倍（行列の大きさ ×4）。ページフォルトの数（`/usr/bin/time`）は nb 192 で 8192：31 万回 ＝ 行列 2 個分の 26 万回に近い（`data/a_runs_summary.csv`）。ただし size 8192 nb 192 のカーネル時間は 24〜45 ms で、計算以外の時間の 22〜37%
- nb 32 では、ページフォルトが行列 2 個分より多く（8192 で 217 万回 ＝ 約 8 倍）、増えた分はタスク数に比例する（1 タスクあたり約 0.34〜0.37 回、p によらない）。`strace` の `mmap`・`munmap` は nb 32 で 8192：約 7,800・7,600 回（nb 192 は 350・210 回）、`sched_yield` はほぼ 1 タスクに 1 回（約 584 万回）。時間は小さい（カーネル全体が 1% 前後）

## 5. 判定（完了条件③）

**c0 の中身（EPYC 7543、nb 192、計算以外の時間 49〜124 ms）**

| | 判定 | 根拠 |
|---|---|---|
| スレッドの生成 | **占める。size によらない固定の時間で、p = 32 で約 6〜7 ms、p = 8 で約 1.4 ms** | FORK の広がり 6.6／1.4 ms、起動の CPU 使用率の立ち上がり。計算以外の時間（49〜124 ms）の、p = 32 で 6〜13%（p = 8 は 1〜4%） |
| QR の終わりの並列度の不足（待ち・CPU 外） | **占める。計算以外の時間の大半**（p = 32・8192 で libiomp5 31 ms ＋ CPU 外 38 ms ＝ 65%） | 試料が最後の 10% に集中、最後のビンの CPU 使用率 38〜100% |
| ページフォルト・カーネル | **占める。計算以外の時間の 15〜37%**（p = 32 で 15〜22%）。size に ほぼ ×4 で増える（3.3〜3.9 倍） | カーネル等の試料、初めの 10% に集中、ページフォルト数。ただしカーネルの中の内訳（ページフォルトか `munmap` か）は分けられていない。strace の `mmap`・`munmap` の時間は 0.18 s 以下（strace による遅れを含む上限）で、カーネル時間（8192・p = 32 で 0.76 コア秒）の 4 分の 1 以下なので、残りの大半はページフォルトとみられる（推定） |
| タイル形式への写し（dlacpy） | **占めると言えない** | `dlacpy_`・`core_dlacpy`・`dlacpy_task` の試料が 0.02 コア秒以下。ただし写しで起きる最初のページフォルトはカーネル側に入る |
| `plasma_workspace_create` の中の `malloc` | **占めると言えない** | libc・plasma 区分が計算以外の時間の 2〜12%、`libc` は size に 3.3〜4.1 倍で増えるが 1〜14 ms |
| `munmap`（free） | **占めると言えない（上限で小さい）** | 上の strace の上限 |
| 分からなかったもの | カーネルの中の内訳、libiomp5 の待ちが「起動」と「終わり」のどちらか（ビン 5%の分解能）、CPU 外の中身（`futex` の眠り、`mmap_lock` の待ち） | |

→ **EPYC 7543 では、c0（nb 192 に残る計算以外の時間）は、「size に比例する」ページフォルト（カーネル）の部分、「size によらない」スレッドの生成の部分、「並列度の不足」の部分の和で、並列度の不足が最大。** 「c0 はタイル形式への写しやページフォルトの時間」とは言えない（写しの CPU 時間は小さい。ページフォルトは計算以外の時間の 15〜37%）。

**τ の中身（EPYC 7543、nb 32、τ 全体 3.5〜3.6 µs、p = 32）**

| | 判定 |
|---|---|
| OpenBLAS の割り当て（`blas_memory_alloc`／`free`） | **占める。τ の約 7 割（2.5 µs）。p = 8 では 0.8 µs（τ の約 2 割）で、p とともに増える。ただしタスク数に比例する定数ではなく（nb 192 では 0.4 µs／タスク）、中身（ロック・探索・メモリ確保）は分かっていない** |
| libiomp5（ランタイムの中） | 占めるが小さい（0.3〜0.4 µs、約 1 割） |
| カーネルの遅れ | **占めると言えない**（0.03 µs。カーネル全体が 1%） |
| 計算が遅くなった分（E_カーネル。nb が小さいとカーネルの効率が低い） | 占める（p = 32 で約 2 割、p = 8 で約 5 割）。nb 32 と 192 の計算の効率の差で、τ ではなく M(nb) 側の原因 |
| 分からなかったもの | `blas_memory_alloc` の中身。`sched_yield` が 1 タスクに 1 回出ている原因（OpenBLAS か libiomp5 か） |

→ **EPYC 7543 では、τ の中身はランタイム（libiomp5）でもカーネルの遅れでもなく、主に OpenBLAS の割り当て（`blas_memory_alloc`／`free`）。** 「τ はタスクの生成」とは言えない（libiomp5 のタスク関係は 1 割）。

## 6. ゼミで言ってよい表現と、言ってはいけない表現

言ってよい（EPYC 7543、p = 32・8、size 4096・8192 の範囲）
- nb 32・p = 32 では、計時区間のオンCPU の約 65% が OpenBLAS の割り当て（`blas_memory_alloc`／`free`）の中。p = 8 では約 20%、nb 192 では 1% 以下
- τ（タスク1個あたりの余分な時間 3.5〜3.6 µs）の約 7 割がこの割り当ての中にあり、libiomp5 は約 1 割、カーネルは 1% 未満
- スレッドの生成は p = 32 で約 6.6 ms かかる（31 本を約 0.2 ms ずつ逐次に作る）。11-10 の「1回目が約 6 ms 長い」と同じ大きさ
- nb 192 に残る計算以外の時間（p = 32・8192 で 106 ms）の大半は、QR の終わりの並列度の不足。ページフォルトを含むカーネルの時間は 2〜4 割

言ってはいけない
- 「c0 はタイル形式への写しやページフォルトの時間」「τ はタスクの生成」（上の判定）
- 「不老・弐でも τ の中身は OpenBLAS の割り当て」（不老・弐の OpenBLAS の設定・ランタイム（libgomp）は未確認）
- 「ページフォルトが c0 の○割」（カーネルの内訳を分けていない。上限・推定の範囲）
- 「BLAS の割り当てがロックの競合」（中身は未確認。呼び出しの頻度で増えることしか分からない）
- 図・スライドでは η でなく E_カーネル・E_並列

## 7. 気になる点・司令塔で相談すること

- **`blas_memory_alloc` の中身を確かめる**（EPYC 7543。無償）。`perf annotate`、`perf record -g`、`OPENBLAS_NUM_THREADS`・環境変数による確認、`/usr/local/lib/libopenblas` のビルドの設定（`USE_OPENMP`・`NUM_THREADS`・`NUM_BUFFERS`）。使われているのは 0.3.30.dev で、`~/Download/build_openblas/` のソースは 0.3.28 なので、ソースで説明できない
- 不老・弐の OpenBLAS（ビルドの設定、`blas_memory_alloc` の有無）の確認は、perf なしでもログ・ビルドスクリプトで可能。不老・弐の追加計測は要らない（有償は相談）
- `reduce_perf.py` の M1T 区間は、計測の終わりの尻尾（プロセスの後始末）を Time で切った。round 2〜5 は M1 区間のまま（尻尾はカーネル等に入り、割合で 0.3〜2.5 ポイントの上乗せ）。主の表は round 1 の 1 回だけで、幅は §2 の再現性の列で見る
- 2点の直線（c0・τ）は nb 32 と 192 の 2 点のみ。nb を増やすと BLAS の割り当てが非線形であることが確かめられる（追加計測なら EPYC 7543 で nb 64・96・128 を perf で）
- STATUS 問題5「τ の中身は未確認」を更新する候補。この計測はゼミの後で STATUS を直す（指示書の決まり）
