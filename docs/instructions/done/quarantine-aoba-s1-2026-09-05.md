# 指示書: AOBA-B s1 データの隔離と進捗の巻き戻し

対象リポジトリ: `tileQR_data`
起票日: 2026-09-05
起票理由: `aoba-b_s1_smt-off` の全計測が、意図した 64 コアではなく **16 コアで実行されていた**ことが判明した。

## 1. 何が起きていたか（背景。変更の根拠なので削らずに記録に残すこと）

AOBA-B の計算ノードは NUMA が **NPS4**（8 ノード × 16 コア）で構成されている。
`aoba-b_s1_smt-off` の計測は次のコマンドで行われていた。

```bash
numactl --cpunodebind=0 --membind=0 \
    bash run_benchmark.sh --size ... --threads 64
```

`--cpunodebind=0` は NPS4 では **NUMA ノード 0 = CPU 0-15 の 16 コア**しか割り当てない。
つまり 16 コアに 64 スレッドを載せた 4 倍オーバーサブスクリプション状態だった。

### 検証（2026-09-05, par057）

同一ノードで 3 通りのバインドを比較（size=4096, threads=64, nb=264）。

| 指定 | 実際に掴んだコア | ピーク GFlops |
|---|---|---|
| `--cpunodebind=0`（6月と同じ） | **16** | 316.2 |
| `--cpunodebind=0-3` | 64 | 461.0 |
| `numactl` なし | 64 スレッドを 128 コアに分散 | 458.8 |

`numactl --cpunodebind=0 --membind=0 --show` の出力が
`physcpubind: 0 1 ... 15` であることを直接確認済み。

6 月の 5 ノード（par001/002/003/004/006）の size=4096 ピークは 297.98〜316.94。
今日の 16 コア版 316.2 と一致する。nb=264 における ib プロファイル 16 点すべてで
比が 1.04〜1.14（ノード個体差 +7% の範囲内）。64 コア版とは 1.5〜1.6 倍離れている。

**保存されている `lscpu.txt`（NUMA ノード数 2）はログインノードのもので、
計算ノードの構成ではない。** これを計算ノードのものと誤読したことが
発見を遅らせた。ログインノードは NPS1、計算ノードは NPS4。

### 影響しないもの

- `aoba-b_s2_smt-off`（threads=128）は `numactl` を使わず 128 コアに 128 スレッド。**有効**。
- ssrfb / kernel_dtsmqr の計測は threads=1 なので**無関係**。
- AOBA 以外の全機材は無関係。

## 2. 隔離する（削除しない）

### 2.1 対象ファイルを特定する

`aoba-b_s1_smt-off` の qr_sweep 生データすべて。COVERAGE によれば
size 2048 / 4096 / 8192 / 16384 の 4 条件 × 5 ノード = 20 ファイル程度。

パスはリポジトリ構成に従うこと（`raw/` 配下の想定だが、
**実際の配置を `git ls-files` で確認してから**動かす）。

```bash
git ls-files | grep -i 'aoba' | sort
```

ファイル名からは config が読めない可能性がある（`par001_size4096_...csv` 形式）。
その場合は `scripts/ingest.py` が config を決定しているロジック
（ディレクトリ構造か、threads 列か）を読んで、確実に s1 のものだけを選ぶこと。
**s2（threads=128）を巻き込まないこと。** CSV の `threads` 列が 64 のものが s1。

### 2.2 移動先

```
quarantine/aoba-b_s1_oversubscribed_2026-06/
├── README.md          ← 下記を書く
└── （生CSVをそのまま移動）
```

`git mv` を使い、履歴を保つこと。

### 2.3 `quarantine/aoba-b_s1_oversubscribed_2026-06/README.md`

次の内容を書く。

- 何のデータか（AOBA-B, EPYC 7702, size 2048/4096/8192/16384, 2026-06 計測）
- **なぜ隔離したか**: `--cpunodebind=0` が NPS4 環境で 16 コアしか割り当てず、
  64 スレッドを 16 コアで実行していた。ファイル名・メタ上の threads=64 は
  「起動したスレッド数」であって「使用した物理コア数」ではない。
- 上記 1 節の検証表をそのまま転記する
- **再利用の条件**: p（物理コア数）を 16 として扱うなら分析に使える可能性はある。
  ただし 4 倍オーバーサブスクリプションは通常の p=16 実行とは別条件であり、
  そのまま `p=16` のデータとして混ぜてはならない。使う場合は必ず
  「oversubscribed 4x」であることを明示する。
- 参考: p=16 と置いて s1/s2 の nb_opt 比から m を逆算すると
  size 8192 で m ≈ 0.235、size 4096 で m ≈ 0.32 となり、
  現行フィット値 0.240 と整合する。この一致自体が 16 コア説の傍証になっている。

### 2.4 ingest から除外されることを確認

`scripts/ingest.py` が `quarantine/` を走査対象に含めていないか確認する。
含んでいるなら除外パスを追加する。除外したことをコードコメントに書く。

## 3. 進捗を「未計測」に戻す

### 3.1 `plan.yaml`

`aoba-b_s1_smt-off` の 2048 / 4096 / 8192 / 16384 が
**未計測として再び計画に現れる**状態にする。plan 側に「達成済み」を持たせて
いないなら変更不要（COVERAGE が生データから数えるはず）。持たせているなら消す。

### 3.2 `machines.yaml`

`aoba-b_s1_smt-off` の `configs` に、今回判明した交絡要因を追記する。

- `numactl`: 旧 `--cpunodebind=0`（NPS4 で 16 コア）→ 新 `--cpunodebind=0-3`（64 コア）
- `nps`: 計算ノードは NPS4（8 NUMA ノード × 16 コア）。**ログインノードは NPS1 なので混同しないこと**
- `cores_effective`: 実際に使用した物理コア数。`threads` とは別概念として持たせる

`cores_effective` が新しいキーになるなら、他の全 config にも
`cores_effective = threads / (smt ? 2 : 1)` 相当の値を入れて統一すること。
**この区別が無かったことが今回の見落としの直接原因**なので、
スキーマとして持たせる価値がある。

### 3.3 `TODO_REMEASURE.md`

手書きファイル。次の 5 条件を追記する。

| config | threads | size | 理由 |
|---|---|---|---|
| `aoba-b_s1_smt-off` | 64 | 1024 | 未計測 |
| `aoba-b_s1_smt-off` | 64 | 2048 | 16 コアで計測。要再計測 |
| `aoba-b_s1_smt-off` | 64 | 4096 | 同上 |
| `aoba-b_s1_smt-off` | 64 | 8192 | 同上 |
| `aoba-b_s1_smt-off` | 64 | 16384 | 同上 |

s2 側の既存の穴（1024 / 2048 / 8192 の nb 範囲不足）も同じ表に併記しておくと、
AOBA でやるべきことが 1 箇所にまとまる。

python scripts/validate.py     # 整合を確認

`derived/optima.csv` から `aoba-b_s1_smt-off` の行が消えること、

## 4. 再発防止

### 4.1 `scripts/validate.py` に検査を足す

現状は「ファイル名と中身の一致」を見ている。これに加えて、
**メタに記録された実効コア数が threads と矛盾していないか**を検査したい。

ただし現行の CSV は `threads,size,nb,ib,GFlops` の 5 列しかなく、
実効コア数の情報を持っていない。よって検査するには計測側の変更が必要。
**この節は「計測側（plasma-bench）への要求」として issue 化するに留め、
validate.py の変更は行わなくてよい。** 内容は次の通り。

> 計測時に `numactl --show` の `physcpubind` の個数を meta として記録し、
> `threads` と一致しない場合は計測開始前にエラーで停止する。

### 4.2 記録

`RESEARCH_LOG.md`（vault 側）に 1 行残す。このリポジトリの作業ではないので、
**このリポジトリでは何もしない**。指示書の最後に「vault 側にログを書くこと」と
書いておくだけでよい。

## 6. やらないこと

- **生データの削除**。隔離のみ。
- **s2 データへの変更**。有効なので触らない。
- **ssrfb / kernel_dtsmqr データへの変更**。無関係。
- **nb_opt の値そのものの書き換え**。隔離すれば derived は自動で作り直される。
- **`p=16` としてのラベル付け替え**。オーバーサブスクリプションは
  通常の p=16 とは別条件。判断は再計測後に改めて行う。
