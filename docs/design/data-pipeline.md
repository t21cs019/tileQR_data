# データパイプライン: raw_data → raw → derived

`README.md` の構成図から移設。`raw_data/` から `derived/` までの組み立て方を扱う。

---

## 測定種別を第一階層で分ける理由

`qr_sweep` と `kernel_dtsmqr` は **スキーマが完全に同一**（`threads,size,nb,ib,GFlops`）で、
データの中身からは区別できない。全体QR分解の測定かカーネル単体の測定かは
置き場所でしか担保できないため、混ぜてはいけない。

走査範囲も違う。qr_sweep は nb=20 から、kernel_dtsmqr は nb=4 から。

`ssrfb` だけは `Time_sec` 列を持つので中身から判別できる。
それでも同じ規則で置き場所を分ける（判別方法が種別ごとに違うと事故のもと）。

| 種別 | 列 | ib の上限 | 置き場所 |
|---|---|---|---|
| `qr_sweep` | `threads,size,nb,ib,GFlops` | `nb/2` | `{config}/` |
| `ssrfb` | `+ Time_sec` | `nb/2` | `{node}/` |
| `kernel_dtsmqr` | `threads,size,nb,ib,GFlops` | `nb - step` | `{node}/` |

## raw_data → raw の組み直し（assemble.py）

計測機から回収した原本は `raw_data/` に置き、**触らない**。
`scripts/assemble.py` がそこから `raw/` を組み立てる。

### 置き場所が計測構成の宣言（重要）

```
raw_data/{config}/xxx.csv
```

ディレクトリ名は `spec/machines.yaml` の `configs` のキーと**完全に一致させる**。
これが計測構成の唯一の宣言で、そのまま `raw/qr_sweep/{config}/` の行き先になる。

```
raw_data/
├── aoba-b_s1_smt-off/        # 64 スレッド（片ソケット固定）
├── aoba-b_s2_smt-off/        # 128 スレッド（両ソケット）
├── i7-7700_s1_smt-on/
├── i7-7700_s1_smt-off/       # 新しい構成はディレクトリを足すだけ
└── ...
```

**なぜスレッド数から推測しないか。** 以前は `i7-7700` で `th<=4` なら smt-off、
`calc` で `th<=12` なら s1、という推測をしていた。これは原理的に当てにならない。
SMT を有効にしたまま4スレッドで走らせれば i7-7700 の `th` は 4 になるし、
2ソケット機で12スレッドを使えば calc の `th` は 12 になる。

**SMT の有無と使用ソケット数は CSV にもファイル名にも残らない。**
実行時の起動方法の事実であって、データからは復元できない。推測でしのげていたのは
「そういう回し方はしない」という暗黙の約束があったからで、smt-on/off と s1/s2 の
変種が増えるほどこの約束は破れやすくなる。計測した人が置き場所で宣言する。

**なぜファイル名や sidecar meta ではないか。** 構成は同一条件の何十ファイルに
共通する定数軸なので、ファイルごとに書くと同じ文字列を複製し続けることになる。
`raw/qr_sweep/{config}/` で既に採っている「変わらない軸はディレクトリに畳む」を
入力側にも適用する。

**宣言が正しいことは検査で担保する。** `make validate` が、
ディレクトリ名が `configs` にあるか、中のファイルの `node` がその構成と同じ
アーキテクチャか、qr_sweep のスレッド数が計画と合うかを見る。

これが無かったころ、dogwood（i7-6900K）のファイルが `benchmark_epyc/` に
置かれていた。ディレクトリ名を誰も見ていなかったので誰も気づかなかった。

### ssrfb はどこに置くか

`ssrfb` は `threads=1` で構成に依存せず、行き先も `raw/ssrfb/{node}/` なので、
どの構成のディレクトリに置いても出力は変わらない。そのマシンの代表構成の
ディレクトリに入れる。二重に取り込めば `validate` の重複検査が拾う。

```bash
python scripts/assemble.py raw_data              # dry-run
python scripts/assemble.py raw_data --apply --clean
```

`--clean` は **`raw/ASSEMBLED.txt`（前回 assemble.py が置いたファイルの台帳）に
載っていたものだけ**を掃除の対象にする。除外したデータは前回の台帳に載っている
ので消えるが、自分が置いた覚えのないファイルには触らない。

ディレクトリ単位で持ち物を決めてはいけない。`raw/qr_sweep/ryzen7-5800x_s1_smt-on`
には `migrate.py` が学部時代のファイルを成形した `..._nodate_r{k}.csv` と、
いまの計測機が規約どおりの名前で出したものが**同居している**。元ファイル
（`Ryzen7-5800X_16_2048_trial1.csv` 等）は `SRC_RE` に合わないので assemble は
読まない。ディレクトリごと消す実装だと、この構成の学部時代のデータは
**消えたきり戻らない**。

### `t{N}` はスレッド数ではなくトライアル数だった

旧命名 `par001_size4096_nb20512_t1_...` の `t` は、スレッド数でも何でもなく
**グリッドを何周したか**だった。`t5` のファイルは同じ (nb,ib) の組を5回ずつ
持っている（行 3963 ごとに同じ組が再出現する）。

1ファイル1トライアルに直すため、assemble.py がこれを切り分ける。
切り方は**行数を周回数で割らない**。`(nb,ib)` の再出現を境界として検出する。
5周ぶん揃っていないファイルが実在する（epyc size2048 は 19,628 行で
3963 の倍数にならない＝最後の周が nb=500 で切れている）ため、
等分割だと境界がずれて全周が壊れる。

トライアル番号はファイル名末尾の `_r{k}` に入る。

### 連結は物理ノードをまたぐ（重要）

計測が途中で切れると、その続きは別の日に走る。AOBA はバッチ計算機なので
**再開したジョブには別のノード集合が割り当たる**。したがって
「1本の走査」を復元する連結は、物理ノードをまたぐことになる。

例: size16384 の nb 24-640 は3つに分かれている。

| nb 区間 | 日付 | ノード |
|---|---|---|
| 24-424 | 06-15 | par005, par006, par009, par010, par058 |
| 416-512 | 06-16 | par001, par008, par029, par034, par035 |
| 520-640 | 06-18 | par002, par006, par007, par030, par045 |

重複する nb 416-424 では、ノード間に**実測で中央値 2.7% の差**がある。
95% 帯を論じる尺度と同程度なので、無視できる差ではない。

連結の規則は次のとおり。

- 重複する nb では **nb 区間が広い方**のファイルの値を採る
- 出来上がったファイルの `node` も、区間が広い方のノード名にする
- どのノードのどのファイルが1本になったかは `raw/JOINS.md` に残す

CSV の列には出所を書く場所が無いので、`JOINS.md` が無いとこの情報は失われる。

### 連結しないもの

- **より広い走査の部分集合になっている周**。走査が途中で切れただけの周を
  完走した周に混ぜることになるため、単独の部分トライアルとして残す。
- **nb が1点しかないファイル**。本番前の試し撃ちとみなして取り込まない。

## 命名規則

```
{node}_size{N}_t{threads}_nb{lo}-{hi}_{YYYYMMDD-HHMMSS}[_r{k}].csv
```

例: `par001_size4096_t128_nb20-512_20260607-235252.csv`
   `calc_size1024_t24_nb32-512_20260625-063259_r3.csv`

| 要素 | 意味 |
|---|---|
| `node` | 物理ノード名。`spec/machines.yaml` の `nodes` に定義があること |
| `size` | 行列サイズ N |
| `threads` | **実際に使用したスレッド数**。CSV の中身と必ず一致させる |
| `nb{lo}-{hi}` | nb の走査範囲 |
| タイムスタンプ | 日付と時刻をハイフンで区切る |
| `_r{k}` | トライアル番号。1周しか無いファイルには付けない |

`_r{k}` が要るのは、1つの原本から切り出した周はタイムスタンプが同じになるため。
これが無いと名前が衝突する。

### 旧命名からの変更点

旧: `par001_size4096_nb20512_t1_20260607_235252.csv`

1. **`t1` はスレッド数ではなかった。** これは**トライアル数**だった
   （`t5` ならグリッドを5周ぶん1ファイルに積んである）。
   タイムスタンプ違いの同一条件に見えるファイルが、実際には
   128 スレッドと 64 スレッドで別条件だったのはこのため。
   新命名では `t` をスレッド数に使い、周回は `_r{k}` で表す。
2. **`nb20512` が曖昧。** 20-512 とも 205-12 とも読める。ハイフンで区切る。
3. **日付と時刻の区切りが不明瞭。**

`scripts/validate.py` がファイル名と中身の一致を検査するので、この事故は再発しない。

なお、**ファイル名の nb 範囲は信用しない**。実データが名前より狭いことがある
（`i5-8500_ssrfb_size4096_nb32-768_...` の中身は nb 516-768 だけ、
`par006_size16384_nb24-512_...` の中身は nb 424 で切れている）。
`assemble.py` も `validate.py` も実データの範囲を採る。

## 計測構成をディレクトリで表す（qr_sweep のみ）

`raw/qr_sweep/` 直下のディレクトリ名は計測構成の識別子。

```
{arch}_s{sockets_used}_smt-{on|off}
```

CSV ごとにサイドカーの meta ファイルを置くと、同一条件のファイルが何十個も並ぶ
本研究では同じ内容を複製し続けることになる。そこで
**変わらない軸はディレクトリに畳み、詳細は `spec/machines.yaml` の `configs` に1エントリだけ書く**。
メタデータの実体は「構成の数」だけで済み、CSV が増えても増えない。

### `sockets_used` の定義（重要）

物理搭載ソケット数ではなく、**実際に使用したソケット数**。

AOBA-B は物理的には 2 ソケット 128 コアだが、64 スレッド実行時は
`numactl` で片ソケット相当（NPS4 の4ノード分）に固定している。この場合は `s1`。
L3 の共有単位（shared-tile cache model の `C_unit`）が変わる以上、
モデル上意味を持つのは使用ソケット数の方であるため。

### 必ず記録する交絡要因

「メモリチャネル構成が GFlops だけでなく最適 nb そのものを変える」
「ターボの有無で再現性が崩れる」ことが分かっている。`configs` に必ず書く。

`memory_channels` / `turbo` / `numactl` / `smt` / `cores_effective`。

`cores_effective`（2026-09-05 追加）は「実際に使用した物理コア数」で、
`threads`（起動したスレッド数）とは別概念として持つ。両者が一致しない
事故が実際に起きた（`docs/design/excluded-data.md` の aoba-b_s1 の例）。

`unknown` のまま残っている構成は `docs/COVERAGE.md` の
「交絡要因が未確認の構成」に出るので、埋め忘れに気づける。

## ダッシュボード（plasma-perf）との対応

向こうの `cpus.toml` が CPU 諸元、`sources.toml` がソース定義を持つ。
同じ機材を両方で定義しているので、食い違うと同じ計測を別物として扱うことになる。
対応は次の2フィールドで明示する。

| ここ | 向こう |
|---|---|
| `architectures.*.dashboard_cpu` | `cpus.toml` のキー（例 `epyc_7702`） |
| `nodes.*.source_key` | `sources.toml` のキー（例 `aoba_b`） |

**node 名はハイフン、`source_key` はアンダースコア。** `sources.toml` のキーは
`i3_6100` だが、ここの node 名は `i3-6100` でなければならない。
ファイル名の node 部分が `[A-Za-z0-9-]+` に限られているため
（`io.FILENAME_RE`）。`validate.py` がこの取り違えを弾く。

### validate.py が見る machines.yaml の整合

- node 名がファイル名に使える文字か
- node / config が参照する architecture が定義されているか
- L3 の算術が合うか（`コア数 / cores_per_ccx × l3_mb_per_ccx == l3_mb_per_socket`）

最後のものは実際に効いた。`epyc-7543` を `cores_per_ccx: 8` と書くと
L3 総量が 128MB になり、`cpus.toml` の 256MB と食い違う
（7543 は CCD あたり4コアのみ有効）。L3 の共有単位は
shared-tile cache model の `C_unit` そのものなので、ここがずれるとモデルが狂う。

## raw/ の自動生成ファイル

| ファイル | 内容 |
|---|---|
| `raw/JOINS.md` | 連結の出所（上記「連結は物理ノードをまたぐ」参照） |
| `raw/CURATION.md` | `spec/curation.yaml` の適用結果 |
| `raw/ASSEMBLED.txt` | assemble.py が前回置いたファイルの台帳。`--clean` の掃除範囲を決める |

いずれも `scripts/assemble.py` が生成する。手で編集しない。
