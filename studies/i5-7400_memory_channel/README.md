# i5-7400 のメモリチャネル構成が qr_sweep に与える影響

計測日 2026-08-31。`raw/qr_sweep/i5-7400_s1_smt-off/` の 2026-06-24 分が
**シングルチャネルで計測されていた**ことを実機で確定させた記録。

## 結論

1. 6月データはシングルチャネル。DIMM を1枚抜いた状態で6月の値が再現した（比 1.003）。
2. チャネル構成の効果は **nb 依存**（nb=32 で +5.9%、nb=448 で +21.4%）。
   一様なスケールではないので **nb\* が動く**（測定10点内で 232 → 320）。
3. したがって 6月の i5-7400 qr_sweep は他機と比較できない。全サイズ再計測が必要。

## 方法

同一マシン・同一バイナリで DIMM の枚数だけを変え、代表10点を5トライアル計測した。
トライアルごとに計測順をランダム化している（順序バイアスと熱ドリフトの排除）。

- 実行経路: `plasma_perf.benchmarks.tileqr.runner.TileQRBenchmark.run_point`
  （6月に使われた旧 `src/core/run_time_dgeqrf.py` とコマンド・環境変数・
  パースまで同一であることを git 履歴で確認済み）
- 条件: `dgeqrf --dim=4096x4096`, `OMP_NUM_THREADS=4`
- PLASMA 25.5.27 + OpenBLAS 0.3.28 (haswell kernel)、いずれも 2026-06-24 10:21 build。
  6月のスイープ（同日 16:25 開始）以降変更なし。

### メモリ構成

`sudo dmidecode -t 17` による。2枚とも同一型番 `D4-2400-4GB.512X8-L`、
DDR4-2400、single rank、Configured Memory Speed 2400 MT/s。

| 状態 | DIMM |
|---|---|
| ch2（出荷構成・現在） | ChannelA-DIMM1 (BANK 1) + ChannelB-DIMM1 (BANK 3) |
| ch1（実験） | ChannelA-DIMM1 のみ。ChannelB-DIMM1 を物理的に抜去 |

### 交絡の排除

チャネル以外が変わっていないことを毎回確認した。

| 項目 | ch2 | ch1 |
|---|---|---|
| 全コア AVX2 クロック（10秒負荷中） | 3300 MHz | 3300 MHz |
| `core_throttle_count` の増分 | 0 | 0 |
| `intel_pstate/no_turbo` | 0 | 0 |

さらに固定点（nb=192, ib=48）を18分連続実行してドリフトが無いことを確認した
（-0.1%、throttle 0件、パッケージ温度 61→73℃ で飽和）。
6月データ自体も同一ファイル内の trial1→trial5 で 1.000→0.998 とドリフトが無く、
スイープ内の熱ドリフト説は棄却されている。

## 帯域の実測

`OMP_NUM_THREADS=4`、48M要素×3配列（1.15 GB、L3 6MB を大きく超える）。
TRIAD/COPY は RFO を含めて計上（それぞれ 32B/24B per iteration）。

| | TRIAD | COPY | READ |
|---|---|---|---|
| ch2 | 29.44 GB/s | 29.05 GB/s | 24.78 GB/s |
| ch1 | 15.53 GB/s | 15.10 GB/s | 16.69 GB/s |
| ch2（DIMM を戻したあと再確認） | 28.98 GB/s | 28.56 GB/s | 24.65 GB/s |

READ のスレッドスケーリングが判定に一番効く。

| threads | 1 | 2 | 3 | 4 |
|---|---|---|---|---|
| ch2 | 6.78 | 13.19 | 19.41 | 24.78 GB/s |
| ch1 | 6.59 | 12.49 | 16.91 | **16.84** GB/s |

ch1 は3スレッドで飽和し4スレッドで伸びない。ch2 は4スレッドでも伸び続ける。
DDR4-2400 シングルチャネルの理論ピークは 19.2 GB/s なので、
ch2 の READ 24.78 GB/s は1チャネルでは物理的に到達不能。

## 結果

`summary.csv` に同じ表がある。size=4096、threads=4、各5トライアルの平均。

| nb | ib | 6月 | ch1 | ch2 | ch1/6月 | ch2/ch1 |
|---|---|---|---|---|---|---|
| 32 | 8 | 24.11 | 23.61 | 25.01 | 0.979 | 1.059 |
| 32 | 16 | 31.10 | 30.64 | 33.09 | 0.985 | 1.080 |
| 64 | 16 | 56.75 | 56.46 | 62.09 | 0.995 | 1.100 |
| 64 | 32 | 61.46 | 61.97 | 69.02 | 1.008 | 1.114 |
| 128 | 32 | 83.50 | 84.82 | 92.31 | 1.016 | 1.088 |
| 192 | 48 | 96.91 | 98.20 | 108.16 | 1.013 | 1.101 |
| 224 | 56 | 97.34 | 98.59 | 109.57 | 1.013 | 1.111 |
| 232 | 48 | 98.87 | 99.58 | 110.97 | 1.007 | 1.114 |
| 320 | 64 | 95.17 | 95.55 | 112.30 | 1.004 | 1.175 |
| 448 | 112 | 87.40 | 88.60 | 107.57 | 1.014 | 1.214 |
| | | | | **平均** | **1.003** | **1.116** |

### 1. 6月 = シングルチャネル

`ch1/6月` は平均 1.003、範囲 0.979〜1.016。10点すべてで再現した。

### 2. チャネル効果は nb 依存

`ch2/ch1` は nb とともに単調増加する（1.059 → 1.214）。
タイルが大きいほどデュアル化の恩恵が大きい。

この10点の中での最良点は **ch1 で nb=232、ch2 で nb=320**。
ピーク性能は 99.58 → 112.30 GFlops (+12.8%)。
`machines.yaml` の「メモリチャネル構成が最適 nb そのものを変える」という
想定に対する実測の裏付けになる。

### 3. 単純なルーフラインでは説明できない

dtsmqr の演算強度の下界 `nb/8 flops/byte` から必要帯域を見積もると、
nb\* 近傍で 2〜3.5 GB/s。シングルチャネルの実効 ~15 GB/s に対して2割程度で、
この見積りは「影響は数%以内」と予測する。実測は 6〜21% でありこれを大きく超える。
演算強度だけのモデルはレイテンシとバンク並列性の寄与を取りこぼすので、
チャネル構成の影響は見積りでなく実測で判断すること。

## データ

- `summary.csv` — 上の表
- `ch2_raw.csv` — ch2 側のトライアル単位の生データ（10点 x 5トライアル）

ch1 と ch2 初回計測のトライアル単位の生データは、DIMM 交換に伴う再起動で
作業ディレクトリごと失われた。`summary.csv` の平均値が一次記録である。

`ch2_raw.csv` は DIMM を戻したあとに取り直した3回目の計測。
`summary.csv` の ch2 列と比が平均 1.003（範囲 0.988〜1.021）で一致しており、
デュアル側の値の再現性の確認にもなっている。
ch1 側を再取得する場合は DIMM を1枚抜いて `spotcheck.py` を回す。

## 再現手順

```bash
python3 studies/i5-7400_memory_channel/spotcheck.py --out /tmp/ch.csv
```

DIMM を抜き差しして2回走らせ、比を取る。実行前に必ず
帯域（`stream.c` 相当）と負荷時クロックを記録し、チャネル以外が
変わっていないことを確認すること。
